# План обучения Backend-разработке на Node.js (с заданиями)

## Подход и ожидания
Ты фронтенд-разработчик ~2 года, поэтому план ориентирован на перенос навыков: HTTP/REST, TypeScript, работа с API. Основной фокус backend’а:
`серверный runtime (Node.js)`, `HTTP/контракт`, `данные и моделирование`, `аутентификация/авторизация`, `тестирование`, `безопасность`, `производительность`, `деплой и эксплуатация`.

## Стек (рекомендуемый)
Чтобы план был максимально практичным и единообразным, предлагаю один трек:
- **Node.js + TypeScript**
- **Express** (routing, middleware, error handler, Swagger через swagger-ui-express)
- **PostgreSQL** + **Prisma**
- **Docker / docker-compose**
- **Auth**: JWT access + refresh, bcrypt/argon2
- **Тесты**: Jest + Supertest (integration)
- **Очереди/фон** (опционально в середине/конце): BullMQ + Redis
- **Документация API**: Swagger (OpenAPI)

## Учебный проект (сквозная “нить” на весь план)
Будем наращивать один репозиторий: **REST API сервиса “Task Manager”**.

Модульная функциональность (по мере обучения):
1. Регистрация/логин пользователей
2. CRUD задач
3. Поиск/фильтры/пагинация
4. Роли (user/admin) и права доступа
5. Обновление токенов (refresh)
6. Загрузка файла (опционально)
7. Кэширование (опционально)
8. Фоновые задания (опционально)
9. Наблюдаемость: health/readiness, structured logs
10. Финальное улучшение: OpenAPI + versioning + нагрузочные тесты

## Чекпоинты
- Каждую неделю есть **конкретные задания**.
- Каждые 2 недели: мини-ревью “что сделано” и “что улучшить”.
- В конце: запуск через `docker-compose up`, тесты, документация.

## Неделя 1. HTTP, роутинг, обработка ошибок (2–7 дней)
**Цели:** понять контракт API и “контроль трафика”.

**Как делать (кратко):**
- Реализуй единый error middleware Express (обработчик с сигнатурой `err, req, res, next`) и проверь на кейсах “невалидный запрос”.
- Разведи код на роуты (`/users`) и middleware: логирование и correlation-id делай до роутов.

**Где брать информацию:**
- Express docs: Routing, Middleware, Error handling.
- Zod docs (или class-validator docs, если выбираешь их).

**Задания:**
1. Реализуй глобальную обработку ошибок:
   - единый формат ответа (например: `{ "error": { "code": "...", "message": "..." } }`)
   - корректные status codes (400/401/403/404/409/500)
2. Создай router/эндпоинты `users` (пока без БД):
   - `POST /users/register` (заглушка)
   - `POST /users/login` (заглушка)
3. Валидация входных данных:
   - DTO (class-validator или zod)
   - запрети пустые/невалидные значения (email, password min length)
4. Middleware:
   - добавь correlation-id (если нет — генерируй)
   - залогируй duration для каждого запроса
5. Добавь CORS с понятной политикой.

**Критерий готовности:** ошибки отваливаются в одном формате, DTO валидируют вход.

## Неделя 4. Аутентификация и авторизация (4–7 дней)
**Цели:** сделать реальный security слой.

**Как делать (кратко):**
- Реализуй auth по “цепочке”: register -> login (JWT access) -> access protected endpoints -> refresh -> logout (revoke).
- Ролевую модель делай как отдельный middleware, который проверяет `role` и ownership (`userId`) до выполнения бизнес-логики.

**Где брать информацию:**
- OWASP Cheat Sheet: Authentication и Authorization.
- JWT best practices для refresh tokens: access короткий, refresh длинный, revoke при logout.

**Задания:**
1. Регистрация:
   - password hashing (bcrypt/argon2)
   - защита от регистрации email повторно (409 Conflict)
2. Логин:
   - проверка пароля
   - выдача access token (JWT)
3. Middleware:
   - `AuthMiddleware` для доступа к задачам
4. Refresh token flow:
   - хранение refresh token (в БД или в secure storage — в рамках проекта достаточно в БД)
   - `POST /auth/refresh` -> новые access token
   - invalidate refresh при logout
5. Роли:
   - `admin` видит (опционально) больше данных
   - `user` видит только свои задачи
   - `RolesMiddleware` + policy-функции (проверка прав по роли)
6. Негативные кейсы:
   - неверный пароль
   - просроченный access token
   - попытка читать чужие задачи (403 или 404 — выбери и придерживайся)

**Критерий готовности:** API защищен, tokens корректно обновляются, роли работают.

## Неделя 6. Безопасность и надежность (3–7 дней)
**Цели:** закрыть типовые ошибки в API.

**Как делать (кратко):**
- Добавь security headers (helmet) и rate limiting, затем проверь негативные сценарии (перебор логинов, слишком длинный input).
- CSRF: для JWT в `Authorization` header обычно достаточно правильной CORS-политики и защиты от инъекций/валидации; зафиксируй это в README.

**Где брать информацию:**
- OWASP Cheat Sheet: Security Headers и Rate Limiting.
- Документация helmet и express-rate-limit.

**Задания:**
1. Helmet / security headers (минимально).
2. Rate limiting:
   - на `POST /auth/login`
   - на общий входной трафик (опционально)
3. Ограничения входа:
   - max длина строк
   - ограничь количество/размер элементов в массивных полях
4. CSRF: объясни (в README), что ты выбрал для токенов:
   - если JWT в Authorization header — CSRF обычно не так актуален
5. Проверка idempotency на “опасных” операциях (минимально):
   - например, как обработать повторный `refresh` или повторный `register`
6. Санитизация сообщений ошибок:
   - не светить внутренние stack traces клиенту.

**Критерий готовности:** security-поведение объяснено и подтверждено через тесты/инструменты.

**Где брать информацию:**
- Redis docs: caching patterns (TTL, invalidation).

**Задания (опционально, но желательно):**

   - `GET /tasks` по query (простая стратегия ключей)
   - TTL + инвалидирование при изменениях
2. Redis (если делаешь кэш):
   - внедри через модуль/DI
3. Node.js основы, которые пригодятся на backend:
   - event loop: понимай, почему “blocking” ломает latency

4. Ограничение параллельных задач:
   - если есть bulk endpoints — ставь лимиты

**Критерий готовности:** API быстрее на чтениях (есть обоснование, как именно).
